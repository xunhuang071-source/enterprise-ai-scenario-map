# 合成示例：从行业底座到企业目标流程

**仅演示调用和设计方法，不是真实客户调研、客户确认、实测AI能力或已实现收益。**

## 起点与裁剪

假设企业采用第三方商家平台模式。先选内置国内电商V0.1，只取10.3商家结算分支，而非把全行业193节点当成企业已开展业务。

1. 初始化带来源的企业骨架初稿，节点使用项目BP ID，全部hypothesis。
2. 按合成企业命名调整主过程；保留来源及企业稳定ID，不改通用底稿。
3. 假设差异涉及非结构化条款和退补说明，提出语义研判任务；如果只有固定规则核算，就不采用这个AI候选。
4. 增加明确标target的人工复核和反馈任务；这些是目标设计，不伪装成企业现状。

## 目标流程

研判结算差异与核验依据 → 人工复核并批准异常处置 → 记录反馈并维护回归样本 → 反馈至研判与知识修订。

这是有反馈的业务流，不是APQC/ECOM编号顺序。分类parent_id与目标relations分别保存。

- AI：解释差异、引用依据、指出缺项和不确定性。
- 人：复核合同适用性与金额、决定处置、承担授权责任。
- 资金：由获授权人员和既有系统执行，不由模型自行划款。
- 验证：原因识别质量、证据正确性及含人审返工的业务工时。当前真实基线、阈值、评分和就绪项均未知。

## 场景组织

一个大场景“商家结算差异人机协同闭环”，以同一个用例ID贯穿近期受控验证、中期岗位复用和远期稳定闭环。

只有一个原子AI用例“商家结算差异研判数字员工”。人工复核、记录反馈不是为凑数量再包装成两个AI。未挂用例的过程保留其业务位置，继续评估是否需要AI。

来源evidence说明V0.1编制底座，不证明客户存在所设痛点。用例通过business_process_refs挂到企业任务，而不是拿ECOM-10.3直接代替企业流程ID。

## 实际复现

以技能目录为工作目录，显式指定一个**尚不存在且在技能之外**的输出目录：

```bash
python3 tests/process_backbone_demo.py --output-dir "PROJECT/流程骨架合成演示"
```

将实际调用init-project、tailor、coverage、scenario_tools validate、project-get，输出两版骨架、裁剪操作、场景投影、挂接检查、联合校验和调用记录。重复使用同一路径会拒绝覆盖。

结构校验通过只证明这些接口和映射一致，不证明未来流程有效或业务收益成立。真实客户仍需确认职责、实际样本、控制要求和验证结果。

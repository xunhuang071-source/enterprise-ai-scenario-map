# 客户确认、版本基线与评审

## 确认与回收

1. 先确认业务框架，再确认场景；拆并影响行数的先处理，再改名与完善描述。
2. 归并／拆分展示原文、理由、选项和推荐。框架由顾问组织，场景内容及建设决定由客户确认。
3. 责任部门、建设方式、年度、预算有明确依据才预填供确认，没有则留空；趋势和模拟内容进入候选建议。
4. 有反馈部门采用回收版，无反馈采用发出版；冲突保留依据和待核实项。动手前读取最新版、逐单元格比较手工修改，保留标记和已确认措辞。
5. 正式建设内容不增不减：建立“确认场景 → 大场景／目标态 → 正文／计划／图”映射。候选不冒充已批准任务；确认项不能因精简漏掉。
6. 内部映射、缺口、修改依据放一份项目记录。JSON 仅作派生投影，不再创建另一份可独立编辑的客户基线。

## 三层一致与三角互查

- 目标模式／蓝图 ↔ 用例：模式中的能力有场景支持；场景变更回调模式。
- 用例 ↔ 计划：每组确认内容有落点，每项任务有来源，同物同名。
- 模式 ↔ 计划：节奏不超出模式边界；总目标各期有对应支撑。
- 文 ↔ 图／索引：变更同步，删除也同步清理总起句、蓝图、计划和色块。
交付前做对照表逐项核查，不以抽样代替场景覆盖检查。确定性项目用脚本，专业语义与客户口径由主模型／顾问逐条判断。

## 三轮评审

1. **方向与业务**：定位、业务归属、目标合理性、投入与保障、接口重叠、重点是否抓住。
2. **语言与逻辑**：分类轴、命名、动宾搭配、数词、段落层级、同物同名。
3. **要素与验证**：输入、AI 动作、产出、人员职责、交接、KPI、测试基准、确认和来源。
各轮独立留批注与总结：视角、标准、问题分布、遗留事项。先齐规格，再齐收口，最后精修文字。
外部旧版评审可取结构判断，不回退已确认表述；已修复的问题不算新意见。

## 批注纪律与失败编码

批注逐条回复，客户手工修改保留。单点问题抽象成规则后全篇扫描；内容冲突先核实，不当作文字润色擅改。
- 若精简删除输入／产出／AI 作用／测试 → 恢复必要信息，只删修饰。
- 若能力、技术、组织载体混层 → 统一分类轴，综合项目用跨域引用表示。
- 若一个用例并列多个独立输出／使用任务 → 拆分预警；任务内步骤不机械拆。
- 若结尾只是“提升水平” → 补可观察结果与验证，不编数字。
- 若名称变化 → 保留 ID，级联同步底稿、正文、图表和文件名。
- 若确认字段缺失 → 登记补证与验证动作，不替客户定责任与年度。
- 若与确认内容冲突、疑似非 AI → 提核实和处置选项，不默默删场景。
- 若标题拿不准 → 给适量备选和推荐，不强改已确认名称。
- 若直接照抄同行／上级 → 检查本级主语、业务领域、抓手、目标与依据，逐项适配。

常见问题：压缩失真、AI 属性不清、主语悬空、结果空泛、标题套路、父子同层、口径漂移、虚构建设物、无测试设计。
